# Правила работы с проектом

## Начало каждого задания

1. Прочитай этот `AGENTS.md`, затем `SPEC.md` до изменений файлов, установки зависимостей и запуска скриптов.
2. Проверь реальные файлы проекта и результаты предыдущих проверок. Отметка в плане сама по себе не доказывает, что реализация работает.
3. Определи область задания и необходимые проверки. Кратко сообщи пользователю, что изменяешь и зачем.
4. Сопоставь новый промпт с существующими именами, интерфейсами, настройками и архитектурой. Сохраняй совместимость с реализованными компонентами.
5. Если обнаружено существенное противоречие, объясни его и уточни решение. Прямые инструкции пользователя имеют приоритет; согласованные изменения отражай в `SPEC.md`.

## Перед запуском скрипта или команды проверки

- Сверь действие с правилами этого файла и текущим состоянием `SPEC.md`. Повторно прочитай файлы, если они изменились или их содержание отсутствует в контексте.
- Проверь рабочую папку, необходимые настройки и зависимости. Объясни назначение запуска.
- Не расширяй область работ без соответствующего задания. Не перезаписывай существующую реализацию без изучения.
- Не выводи API-ключи и другие секреты. Настоящий `.env` исключай из Git; в `.env.example` используй только пустые значения или безопасные примеры.

## Документация библиотек: Context7

При вопросах и работе с API, настройками, установкой или использованием библиотек, фреймворков, SDK, CLI и облачных сервисов получай актуальную документацию через Context7, даже если ответ кажется известным.

1. Сначала вызови `resolve-library-id`, если пользователь не предоставил точный ID библиотеки.
2. Выбери наиболее релевантный официальный источник с хорошей репутацией и подходящей версией.
3. Вызови `query-docs` с конкретным вопросом. Разные независимые темы запрашивай отдельно.
4. Используй полученную документацию при реализации.

Context7 не требуется для общих концепций программирования, чистого рефакторинга, проверки бизнес-логики или code review без вопросов о библиотечных API.

## Взаимодействие с пользователем

- Кратко сообщай результат изменений, назначение и подтверждённые проверки по существу задачи.
- Выполняй согласованное задание, сохраняя совместимость приложения.
- Отделяй факт успешной проверки от предположения. Заглушки не подтверждают работу реального API или модели.
- Инструменты и агенты приложения должны использовать общие согласованные форматы входных и выходных данных.

## Поддержка документации

- SPEC.md содержит только актуальное техническое описание, контракты и ограничения.
- Не добавляй в публичную документацию историю обсуждений, согласования, разбивку работ по этапам или внутренние планы.
- При изменении архитектуры и контрактов обновляй SPEC.md; инструкции подключения и запуска поддерживай в README.md.
- Сообщай результаты проверок и ограничения в итоговом ответе. Не выдавай предположения за подтверждённый результат.
- Не записывай секреты в документацию, отчёты или Git.
