# Планировщик путешествий — спецификация и состояние

## Цель

Создать учебный проект по мотивам курса Simplilearn «Agent Team Orchestration with CrewAI»: Python-команда планирует путешествие, а веб-интерфейс позволяет задать параметры и наблюдать выполнение.

Основной чат отвечает за объяснения и промпты этапов. Реализация выполняется в отдельных чатах того же проекта. Этот файл — общий план и журнал для всех чатов.

Публичная программа курса подтверждает порядок tools → agents → tasks → processes → crew и пример путешествий. Точный код и состав команды из видео не изучены. Приведённая ниже архитектура — согласованный учебный вариант, а не подтверждённая копия исходников курса.

## Вход и результат

Вход: город отправления, выбранное направление, даты, бюджет с валютой, количество путешественников, интересы.

Результат: маршрут по дням, примерная смета, рекомендации по перемещениям, ссылки на источники. Оценочные цены явно помечаются; актуальные предложения подтверждаются источниками. Бронирование и оплата не входят в первую версию.

## Архитектура первой версии

```text
React → FastAPI (Python) → CrewAI Crew → результат в интерфейсе

Задача 1: исследование направления
    ↓ сведения и источники
Задача 2: логистика и бюджет
    ↓ сведения и расчёты
Задача 3: итоговый маршрут
```

- **3 агента:** исследователь направления; специалист по логистике и бюджету; планировщик.
- **3 основные задачи:** исследовать направление; оценить логистику и расходы; собрать маршрут.
- **3 общих инструмента:** поиск в интернете; чтение веб-страниц; калькулятор расходов.
- Исследователю доступны поиск и чтение; специалисту по бюджету — все три; планировщику — калькулятор.
- **1 Crew**, процесс `Process.sequential`, без отдельного менеджера. Результаты предыдущих задач передаются как контекст следующих.
- Поиск: готовый TavilySearchTool в адаптере InternetSearchTool, только basic, auto_parameters=False; бесплатный тариф настраивается пользователем в Tavily. Чтение: расширенный ScrapeWebsiteTool; расчёты: свой BaseTool с Decimal. MCP для первой версии не требуется.
- Модель и провайдер LLM уточняются на этапе 1. Секреты хранятся локально через настройки окружения.
- Интерфейс: форма поездки, статусы задач, готовые промежуточные результаты, итоговый маршрут и смета.
- Конкретные форматы данных и механизм передачи прогресса определяются до реализации соответствующих интеграций и записываются здесь.

## Этап 5 — реализация и ограничения

- `travel_planner.crew.create_crew(trip, *, llm=None, tools=None, task_callback=None)`
  использует create_agents/create_tasks и возвращает одну Crew Process.sequential:
  research → budget → itinerary. Сохраняет тождественность всех Task/context и
  существующих Agent. Менеджер, делегирование, память, embeddings, planning не
  подключаются; конструирование не вызывает сеть/LLM/tools.
- Callback завершённого бюджета дополняет expected_output планировщика явной
  проекцией проверенного контекста: валюта, известный итог, полнота, статус бюджета,
  превышение, полный список sources и выбранные place_ids. Проекция не создаёт
  фактов/цен, не заменяет context и не отменяет вызов tools или guardrail.
- `travel_planner.runner.run_trip(trip, *, on_event=None, timeout=420,
  max_llm_calls=24)` — синхронная функция для CLI и будущего сервера. Каждый запуск
  в своём spawn-процессе; на Windows в обычном скрипте нужен __main__ guard.
  RunResult содержит status, trip, final, tasks, rejected, events, checks, error,
  worker_stopped. final — ItineraryResult только после полного проверенного успеха;
  tasks содержит валидные завершённые результаты. rejected содержит только
  структурированные кандидаты, отклонённые проверкой согласованности, и никогда
  не является готовым маршрутом. Метод as_dict сериализует Money строками.
- `scripts/run_trip.py examples/trip.json [--output новый.json] [--timeout 420]
  [--max-llm-calls 24]`: вход совпадает с TripInput. Пример — Москва/Казань,
  14–15 ноября 2026, двое, 60000 RUB, архитектура. При использовании после этих
  дат пример нужно обновить. По умолчанию уникальный results/trip-<дата>-<время>-<id>.json;
  рядом *.events.jsonl. Файл резервируется до запросов с режимом x; прежние
  результаты/журналы не перезаписываются. Ошибка журнала помечает резерв failed.
  CLI: 0 успех, 1 ошибка исполнения, 2 ошибка входа/параметров/файлов.
- Поддерживаемые TaskStartedEvent/TaskFailedEvent и task_callback дают события
  задач; ToolUsageStartedEvent/FinishedEvent/ErrorEvent дают фактические tools.
  Доставляются безопасные проекции событий с UTC timestamp, именем задачи/tool,
  статусом, URL/размером текста либо суммами. Родительские итоговые события могут
  не иметь timestamp. Никаких рассуждений, текстов страниц, заголовков запросов,
  сырого SDK и сообщений исключений. Передаются классы/позиции стека и безопасные
  причины guardrail, а не входные значения ValidationError.
- События фильтруются по id задач этой Crew; event bus flush вызывается до проверки.
  Контекст подтверждается как в TaskStartedEvent, так и в реальном исходящем
  HTTP-запросе LLM: наличие raw предыдущих результатов без вывода самого запроса.
  guardrail `_run` калькулятора не считается tool-call агента. Успех требует
  настоящих успешных событий без cache: search+reader у исследователя и calculator
  у budget/planner; проверяются полные суммы статей, валюта и общий бюджет.
- BaseInterceptor установлен при конструировании общей LLM и ограничивает каждый
  исходящий HTTP-запрос, включая дополнительные обращения конвертера/SDK fallback.
  N+1 не отправляется. У SDK max_retries=0; лимиты агентов/guardrail сохранены.
  Преднамеренная остановка LimitReached не поглощается обработчиками Exception.
- Родитель ограничивает всё время процесса (по умолчанию 420 секунд), затем
  terminate/join, при необходимости kill/join. Возврат содержит worker_stopped.
  Это завершает локальные потоки SDK; не отменяет уже отправленный запрос на
  стороне провайдера и не обещает отсутствия начисления за него. Допустимые
  timeout (0,900], max_llm_calls [1,60]. Agent max_execution_time=120 работает через
  ThreadPoolExecutor: future.cancel не останавливает уже работающий поток,
  поэтому одного этого API недостаточно для жёсткого дедлайна.
- Внешний on_event вызывается последовательно daemon-потоком родителя через очередь.
  Ошибка наблюдателя даёт observer_failed и сохранённые промежуточные результаты;
  зависание не мешает остановить worker по дедлайну. После остановки worker
  ожидание доставки ограничено 0.5 секунды. Python не умеет принудительно завершать
